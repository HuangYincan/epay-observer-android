# ADR-0003 自动充值及同金额冲突策略

状态：M0 review candidate；自动充值目标已确认，测试策略待评审，真实收款启用条件未满足。#8。

决定：正常且符合策略的唯一匹配自动确认。人工核对只处理异常，不将“先人工点击每笔订单”写成首个可用版本的主目标。模拟器验收不得注入订单号绕过匹配。

方案比较：A. 金额占用能阻止同时发放冲突单，不能证明静态码付款归属；任何有限冷却期都不能排除旧二维码再次付款。B. 尾数分配改变订单／回调金额，当前 epay-go 对 Amount 严格校验，New API 又有独立金额契约缺口；不纳入首轮。C. 可验证的平台交易标识与订单关联更强，但当前通知不保证提供，不能凭空补齐。

M0 建议选择：隔离合成环境采用 A 的严格子集——同 receiver/provider/金额只分配一次，历史 claim 不因支付／过期／等待而释放；新建冲突单拒绝，不自动改尾数。正常测试付款在来源、绑定、时间、身份均满足时自动充值，不加人工确认。测试前的独立环境初始化不属于每笔支付人工确认，也不能用于真实收款历史清除。

真实 notification 来源目前一律不能获得自动确认资格。即便是首次金额、唯一候选、真实 App 包名，仍可能是无关付款或聊天伪装。后续需要真实样本研究、可审计账户绑定和额外归属证据／明确风险决策；用户没有批准这些假设。本结论是 M0 暴露的产品可行性约束，不能包装为已解决生产自动充值。

核心难题：旧付款可在订单过期后到账；重复通知可能携带新的观察身份；同一应用通知也可能来自聊天。任何有限时间窗都不能自动证明交易归属。无法区分时必须 needs_review，不以最近一单兜底。

具体参数、收银台行为和反例见 SPEC-003；信息不可区分实验见 M0 报告。#8 保持开放等待该范围决策，不能以文档交付代替生产适用性确认。
