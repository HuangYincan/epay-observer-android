# SPEC-044 线上版本New API回调契约的私有修复验证

2026-10-19；#82，承接SPEC-023/036/041/043。目标真实自动充值仍未完成：此前线上版本只读审计发现money不比较、ACK先于处理、订单status和user quota非原子。本批只在与已标注部署revision相同的独立AGPL checkout准备最小补丁；不改既有M3副本、不推第三方上游，不部署或修改线上New API。

后续用户重申仅允许修改epay-go和安卓观察器。本规格保留已完成隔离研究的历史要求，相关线上替换方案已撤回；New API升级不再作为接入前提或待授权事项，后续按既有EPay接口推进。

1. 签名验证保留；成功付款回调必须对比签名money和原topup下单时实际发送的两位小数金额，使用整数分精确比较，拒绝空白/符号/指数/非正/过精度。旧float按下单原FormatFloat规则转换，不把fixture金额带入实际订单。
2. 原订单行锁、支付provider/状态校验、quota有界计算、user行锁及quota范围、topup成功/完成时间与user额度在同一数据库事务提交；缺用户或任一步失败回滚。重复/并发/多连接仅增额一次。使用既有跨SQLite/MySQL/PostgreSQL的lockForUpdate及quota helper，不改其他支付通道。
3. 只有事务提交成功或已完成的等额幂等重复才响应success；失败响应fail供网关持久重试。非成功平台状态不充值。现有缓存没有额度提交版本，删除会丢失待刷消费，提交后增量又可能重复计算并发回填；本最小补丁在RedisEnabled或BatchUpdateEnabled时对pending订单明确fail、零写入，已成功等额重复仍可幂等ACK。仅两者均关闭、各实例配置稳定且旧batch受控排空的模式支持新入账；不自动改线上配置。日志不能触发第二次入账。缓存兼容性尚未解决，完整支持需要另行设计全部额度reader/writer参与的协议。
4. 独立合成HTTP/数据库测试必须核对真实handler响应与数据库状态；覆盖金额反例、正确签名、错误签名、重复/并发、保存/额度更新失败回滚、失败后重试和额度溢出。SQLite与隔离PostgreSQL实测，MySQL优先使用已存在隔离镜像实测，若不可用则SQL方言/镜像条件如实记录，不默认安装新工具。
5. 补丁/构建/日志/源码只存本机私有AGPL产物，不复制到公开MIT实现；记录base/hash/许可和实际测试层次。公开仓库仅规格与脱敏结果。不能把此版本离线通过升级为实际线上代码或余额证据。

本批不是线上New API变更授权。部署须按已有“不改New API”的范围另行明确；准备可审阅补丁、验证与回退方案后才提出具体变更。SPEC-042真实对照、收款可信边界/身份与金额政策仍独立阻塞，不为部署或样本缺失自动置review为1。
