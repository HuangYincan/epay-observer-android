# SPEC-004 自动充值、事务与回调

状态：M0 review candidate。#26/#27；FR-04、FR-05、FR-06。

## 正常路径

合格事件被唯一匹配后，无需逐单人工点击，即完成网关支付确认，并通过现有易支付商户通知使 New API 自动充值。人工核对只处理异常；首个可用测试版本必须展示正常路径全自动完成。

## 事务边界

事件绑定／消费、订单状态、支付确认凭据、商户余额与资金流水必须在同一数据库事务中提交。并发处理同一事件或同一订单只能有一个事务产生收入。不能先调用现有独立提交的 ProcessPayNotify，再另一个事务标记事件已消费。

锁序和唯一约束见 SPEC-003。事务异常时全部回滚；进程在任意步骤退出后重试不重复收入。真实平台流水不存在时单独保存 observer evidence 类型及稳定关联，api_trade_no 保持缺失。不得调用要求非空流水的旧 ProcessPayNotify 并伪造入参；需抽出共享事务内记账函数。provider 流水若可信存在，再加账户/provider 范围唯一约束；单个 event 唯一不等于真实交易唯一。

## 商户通知

固定 epay-go 基线已有 paid + notify_status 条件扫描、数据库 lease/token、过期租约恢复及 worker。优先复用订单行作为持久通知任务，结算事务同时保证 notify_status=pending；goroutine 只加速唤醒，不是可靠性根基。无需再建并行通知队列。金额、商户订单号来自原订单，密钥来自商户记录，APK 不可指定。需测试旧商户 key 轮换期间的验签一致性，不能假设历史 key 已快照。

回调失败只重试通知，不重新记账。New API 测试实例须分别验证错误签名、未重签名的金额篡改、合法签名但金额与原单不符、重复回调和乱序。当前固定 New API 基线有业务金额核对缺口，见集成文档，不能将该项填 Passed。return_url 只跳转。两端数据库独立，通过至少一次投递+幂等接收达到最终一致性，不存在跨库原子提交。

## 可追踪状态

Observer accepted、matched、gateway credited、merchant notify pending／succeeded／failed 分开存储并可查询。测试验收必须同时查看事件、网关订单、资金流水、商户通知和 New API 余额，不能只看支付页面返回成功。

## 异常

匹配歧义／证据不足进入 needs_review；核对需要查看实际收款账单。重复事件不重新开单，不覆盖已确认不同凭据，不恢复已退款订单。测试模式和生产模式各自隔离，测试事件不能进入真实账务。
