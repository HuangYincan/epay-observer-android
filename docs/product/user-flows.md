# 用户流程

状态：合成原型的配对、权限、状态、诊断和后台上传已实现；人工操作入口见[人工验收清单](../testing/manual-acceptance.md)。真实App与自动收款准入仍待验证。

## 设置流程

1. 在隔离的 epay-go 环境创建个人码通道，分别配置微信与支付宝内容。
2. 网关创建观察器设备记录及受限的配对凭据；APK 显示将绑定的网关、收款账户范围和权限。
3. 用户确认绑定，开启 Android 通知使用权；界面分别显示“权限已授予”和“服务已连接”，不能混为一谈。
4. 检查连通性。测试按钮只做连接／鉴权检查，不伪造付款或确认真实订单。
5. 模拟器使用隔离夹具构建，网关与 New API 为测试实例；界面持续标明“测试模式”。

## 合格事件自动充值

New API 创建充值单 → 网关展示收款码与应付金额 → 系统通知被观察 → APK 解析并先落盘 → 网关验证设备／请求 → 持久接收事件 → 匹配唯一合格订单 → 事务记账与消费事件 → 商户通知 New API → New API 校验签名并幂等充值。

APK 不显示“已充值成功”直到服务端给出对应业务状态；“HTTP 请求成功”“事件已接收”“订单已入账”“New API 已通知”必须分开。

## 异常流程

| 触发 | 处理 |
| --- | --- |
| 通知未知／疑似聊天 | 本地忽略或待诊断，不创建可入账事件 |
| 无网络 | 队列持久保存并等待重试 |
| 凭据撤销／配置不符 | 停止上报并提示重新绑定，不无限重试 |
| 同金额多个候选 | needs_review，不按创建时间随便选单 |
| 无候选／过期／时间异常 | 留存明确原因，不在将来自动绑定新订单 |
| 商户通知失败 | 网关独立重试，不重复记账 |
| 人工核对 | 必须核实真实账单并记录操作；不能仅凭同一条可疑通知点“确认” |

主流程是自动充值，人工路径只用于异常。配对/诊断按SPEC-016/019/020；管理员查询/暂停按SPEC-026。当前没有手工将通知确认到账的入口。
