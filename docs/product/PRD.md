# PRD：EPay Observer Android

状态：Draft。日期：2026-10-15。首版范围依据用户确认：微信与支付宝、自动充值、安卓模拟器优先。工期、实体设备、最终技术版本待定。

## 1. Executive Summary

**Problem Statement**：现有 epay-go 个人码通道只能展示静态二维码并接收带订单号的签名回调，没有到账监听及事件到订单的匹配能力。用户希望通过自建安卓 APK，使 New API 的个人码充值形成自动闭环。

**Proposed Solution**：APK 监听允许来源的通知，持久化收款事件并认证上报；网关负责去重、匹配与事务入账，再使用已有易支付通知链路给 New API 充值。无法确定的事件保留待核对状态，不随机选单。

**Success Criteria（规划验收目标，尚未执行）**：

1. 模拟器中的微信形态与支付宝形态合成通知，各完成一条不注入订单号的自动充值闭环。
2. 已批准合成正例全部正确解析；负例、伪装聊天、摘要、退款、无金额与多金额样本自动入账次数为 0。
3. 同一逻辑事件重复 20 次并发上报、响应丢失后重试，网关入账及 New API 余额增加均恰好一次。
4. 离线期间保存 50 条合成事件，恢复网络后不丢事件；过期事件不得匹配新创建订单。
5. 同金额冲突、跨账户／通道、未知规则、时钟异常测试中错误自动入账次数为 0。

这些指标描述测试集内结果，不构成对任意真实通知的保证。真实来源兼容性另设门槛，不由模拟器夹具替代。

## 2. User Experience & Functionality

### User Personas

- 站点运营者：配置收款账户及 New API，希望合格订单自动充值，异常可追踪。
- 开发与测试人员：先在模拟器复现通知、网络与账务异常，拿到可重复的验证证据。

### User Stories / Acceptance Criteria

| 编号 | 用户故事 | Done 定义 |
| --- | --- | --- |
| FR-01 | 作为运营者，我要同时支持微信与支付宝 | 两个独立解析器、两个来源开关、两套正负样本与独立测试结论 |
| FR-02 | 作为运营者，我要知道监听和上报是否工作 | 展示权限、服务连接、待发送、最近成功和错误状态；失联不能显示健康 |
| FR-03 | 作为运营者，我要断网后继续上报 | 事件先落盘；重试不改变事件身份；成功持久确认后才删除队列项 |
| FR-04 | 作为运营者，我要自动充值 | 唯一匹配且符合策略时自动入账并回调 New API，无需逐单人工点击 |
| FR-05 | 作为运营者，我要避免串单和重复充值 | 歧义停止自动确认；事件消费与记账原子完成；重复回调只增加一次余额 |
| FR-06 | 作为运营者，我要能解释异常 | 按事件追踪鉴权、解析、匹配、记账和商户通知；异常有明确原因 |
| FR-07 | 作为开发者，我要先用模拟器验收 | 一键场景说明、隔离夹具、可重跑报告；Release 不含模拟信任入口 |
| FR-08 | 作为运营者，我要控制设备访问 | 绑定、撤销、轮换、丢失后的停止策略均可验证；客户端不持有商户 API Key |

### Non-Goals

不实现资金提现、自动退款、官方平台交易查询、绕过 App 安全机制、Root／Hook、获取聊天数据库、保证所有手机后台永不被杀。当前阶段不发布商店、不接真实资金、不修改 New API 的充值协议。

异常人工核对是兜底，不替代 FR-04。自动匹配策略的具体窗口、复用规则与资金限制仍需 ADR 收敛。

## 3. AI System Requirements (If Applicable)

不适用。首版不使用 AI 推断到账、不向大模型发送通知、不用概率判断直接触发入账。未知通知只能记录为 unsupported／needs_review。

## 4. Technical Specifications

**Architecture Overview**：见 [架构](../architecture/overview.md)。业务模型为“通知观察 → 收款事件 → 匹配决定 → 支付确认 → 商户通知”，每层状态独立。

**Integration Points**：本仓库交付 Android APK、合成夹具、协议规格与测试向量；epay-go 增加事件接收、设备认证、匹配、审计及事务接口。New API 测试实例使用网关商户 ID／API Key，设备使用独立凭据。

**Security & Privacy**：仅处理允许来源；普通通知不上传；密钥安全存储；测试来源仅存在于测试环境；发送端签名不是平台支付证明。参见 SPEC-005。

## 5. Risks & Roadmap

**Phased Rollout**：M0 规格与依赖 → M1 双通道模拟采集 → M2 认证可靠上报 → M3 自动充值测试闭环 → M4 真机验证与发布准备。

**Technical Risks**：通知格式变化、模拟器无法登录真实 App、同金额碰撞、通知伪装、无真实流水号、时钟偏差、OEM 后台限制、跨仓库版本不一致。对应研究、实现和测试任务均列入 [BACKLOG](../issues/BACKLOG.md)。

没有真机证据时只发布“测试闭环已验证”的结论，不能标为真实收款可用。发布与生产启用不属于当前任务。
